# Migrations

Alembic lives here and points at the models in `agent_ant_core.db.models`. The database URL
comes from `DATABASE_URL` (see `.env.example`); no credentials are stored in `alembic.ini`.

| Revision | What |
|---|---|
| `0001` | Baseline: `raw_events` with `idempotency_key UNIQUE` (issue #19) |
| `0002` | `raw_events.related_event_id`: an SMS reply points at its missed call (issue #21) |
| `0003` | `llm_output_audits` + `human_edits`: extraction audit trail (issue #24) |

## Everyday commands

```bash
just db-up                                   # local Postgres (infra/docker, port 5432)
just migrate                                 # alembic upgrade head
uv run --all-packages alembic revision --autogenerate -m "what changed" --rev-id 0002
```

Always read an autogenerated revision before committing it: Alembic misses some changes
(renames, server defaults) and the file is the permanent record of what ran in production.

## Running the database tests

`packages/core/tests/test_raw_events.py` needs a real Postgres, because the guarantee it tests
is a database unique constraint. It runs the migrations against `TEST_DATABASE_URL` and clears
`raw_events` before each test, so **point it at a throwaway database, never one you care about**.
The variable is separate from `DATABASE_URL` on purpose.

```bash
export TEST_DATABASE_URL=postgresql+psycopg://agent_ant:agent_ant@localhost:5432/agent_ant
just test
```

Without it, those tests **skip** locally (look for `skipped` in the summary, not just a green
line) and **fail** when `CI` is set. CI runs a Postgres service and sets the variable.
